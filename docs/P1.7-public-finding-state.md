# P1.7: public finding state (report schema 3)

Normalization runs only in `reporting/finding_state.py` and `json_report.py`.
RawHit.safe_dict(), detector output, CandidatePolicy P1.5, signatures, recovery
objects and checkpoint serialization are unchanged. SCANNER_SEMANTICS_BUMP=NO
(semantics 2), CHECKPOINT_FORMAT_BUMP=NO (format 3).

The old ValidationStatus enum combines structure with rejection and uses
lowercase values. It cannot represent any of the four independent public axes
without changing its meaning. The adapter accepts that enum without modifying it.

| Dimension | Values |
| --- | --- |
| discovery_state | RAW, REJECTED, CANDIDATE, ACCEPTED |
| structural_state | NONE, FRAGMENT, COMPLETE |
| crypto_state | NOT_APPLICABLE, UNCHECKED, VALID, INVALID |
| recovery_relevance | INDEPENDENT, CONTEXT_REVIEW, LIKELY_FALSE_POSITIVE |

COMPLETE describes the particular artifact: a complete WIF or mnemonic is not
a complete wallet. VALID is independent of both structure and recovery relevance.
An unknown status, completeness or relevance raises ValueError explicitly.
Confidence alone never upgrades a finding. Correlation without structural or
cryptographic confirmation does not imply acceptance.

| Existing evidence | Discovery / structure / crypto / relevance |
| --- | --- |
| RAW, UNVALIDATED, ANCHOR_ONLY | RAW / NONE / NOT_APPLICABLE (UNCHECKED for a secret) / CONTEXT_REVIEW |
| REJECTED or target-specific insufficient structure | REJECTED / existing structure / no inferred crypto failure / CONTEXT_REVIEW |
| CANDIDATE | CANDIDATE / NONE / UNCHECKED / CONTEXT_REVIEW |
| FRAGMENT, TRUNCATED, STRUCTURAL_FRAGMENT | CANDIDATE / FRAGMENT / UNCHECKED / CONTEXT_REVIEW |
| STRUCTURAL | ACCEPTED / FRAGMENT / UNCHECKED / INDEPENDENT |
| VALIDATED without completeness evidence | ACCEPTED / NONE / UNCHECKED / INDEPENDENT |
| STRONG, COMPLETE | ACCEPTED / COMPLETE / UNCHECKED / INDEPENDENT |
| CRYPTO_VALID and explicit crypto validator successes | ACCEPTED / independently determined / VALID / independently determined |
| Explicit checksum, scalar, public-key-match failures | REJECTED / independently determined / INVALID / CONTEXT_REVIEW |

Target-specific interpretation:

* Bitcoin Core: weak metadata marker stays RAW; a validated metadata page is
  ACCEPTED/FRAGMENT relative to wallet recovery. Framed key-side validation is
  ACCEPTED but does not validate the private value. Record/page structure does
  not imply crypto VALID. A reconstructed database with legacy STRUCTURAL status
  has complete reachable structure; a STRUCTURAL reconstructed wallet also has
  validated wallet evidence, so both receive COMPLETE. Direct recovery remains
  conservative (FRAGMENT). Valid standalone DER is VALID without claiming a
  complete wallet. Rejected address/pubkey context remains REJECTED; successful
  address/pubkey checks are VALID/CONTEXT_REVIEW and never count as secrets.
* Electrum: BIE anchor alone is RAW; candidate and fragment evidence remains
  CANDIDATE. Parsed complete modern and legacy wallets receive COMPLETE.
  ELECTRUM_CONTAINER_STRUCTURAL_VALID confirms structure, not decryption.
* MultiBit: rejected network/export/HD markers preserve rejection. Protobuf,
  Java and export fragments remain CANDIDATE/FRAGMENT. STRONG protobuf evidence
  maps to ACCEPTED/COMPLETE, with crypto UNCHECKED (no new crypto claim).
* Armory: paper marker is RAW/CONTEXT_REVIEW; rejected binary signature remains
  rejected, structural fragment is CANDIDATE/FRAGMENT, confirmed full header is
  ACCEPTED/COMPLETE. Header validation does not imply crypto validation.
* Mnemonics: BIP39 checksum, Electrum seed version and strict/compat V1 roundtrip
  successes map to VALID. LIKELY_WORDLIST_FALSE_POSITIVE maps independently to
  LIKELY_FALSE_POSITIVE, including in compact report aggregation.
* Legacy logical wallet candidates retain candidate-level structure and receive
  crypto VALID when at least one contained key has been validated. Individual
  crypto validation rows have their own normalized state, including failures.

## Counters and compatibility

`finding_summary` counts canonical `target_findings` before noise aggregation.
It does not add overlapping recovery views, hotspots or raw discovery hits.
`recovery_state_summaries` presents Berkeley recovery views separately.
`structurally_complete` counts artifacts, not wallets. `crypto_valid_occurrences`
includes checked public context; `crypto_valid_secret_occurrences` excludes it.
`crypto_valid_unique_secrets` counts available safe secret fingerprints; it is
not a claimed global cross-format key count. Missing identities are explicitly
counted as `crypto_valid_secrets_without_fingerprint`. Existing per-recovery
crypto counters remain available, including logical wallet keys that have only
public-key identity in the legacy report. No secret bytes are read or exported
to fill in missing fingerprints.

Legacy `rejected_statistics` continues to aggregate likely wordlist noise for
compatibility. Its name is historical: use `finding_summary.rejected` for actual
rejections. Aggregate rows also expose the independent normalized state.

Schema 2 -> 3 adds normalized_state beside existing fields. Wallet-record
offsets remain retained even when rejected. Readers in `src/bfrs/tools` select
legacy fields and ignore additive fields; report schema is not gated to v2.
Revalidation and exporters continue to use their original fields. All report
adapters construct copies, so serializing cannot alter resume state.
